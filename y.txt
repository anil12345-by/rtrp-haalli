# **QUESTION 1 – Deployment using Docker Compose (25 Marks)**

20 Marks – Practical

## **1. What is Docker Compose?**

Docker Compose is a tool used to define and run multiple Docker containers using a single YAML configuration file.

Imagine that we have a web application that requires a MySQL database.

Normally, we need to start both containers separately.

With Docker Compose, we define both services inside one file called:

`docker-compose.yml`

Then we can start both containers using a single command.

### **Architecture**

**User / Web Browser**

[http://localhost:8080](http://localhost:8080?utm_source=chatgpt.com)

[docker Logo PNG Vector (SVG) Free Download](https://images.openai.com/static-rsc-4/R3tE02yQDDdrIl6Y80p2egXN6vwiSR9hKiNlew9xJDHhHCd8CZixMDiOe_pHIFhQZOscJaB4FYXNP06W9P60nxIT5jsSVnyIMRI3Gj2fry6bJ-Z1UcJzVLjvbHqfUZXJNpiT7V7Yl9VplHUBGs4QsgfSbR35dVUxWHcDx7_FPyg?purpose=inline)

**Docker Compose**

Manages multiple services

**Web App**

Port 8080

**MySQL**

Port 3306

Both services communicate through a Compose network.

## **4. Write docker-compose.yml**

This is the main configuration file for the experiment.

```

services:

  web:
    image: your-dockerhub-username/your-web-image:latest
    container_name: web-container
    ports:
      - "8080:8080"
    depends_on:
      - mysql
    environment:
      DB_HOST: mysql
      DB_PORT: 3306
      DB_NAME: studentdb
      DB_USER: student
      DB_PASSWORD: student123

  mysql:
    image: mysql:8.0
    container_name: mysql-container
    restart: always
    environment:
      MYSQL_ROOT_PASSWORD: root123
      MYSQL_DATABASE: studentdb
      MYSQL_USER: student
      MYSQL_PASSWORD: student123
    ports:
      - "3307:3306"
    volumes:
      - mysql-data:/var/lib/mysql

volumes:
  mysql-data:

```

**Important:** Replace `your-dockerhub-username/your-web-image:latest` with the actual web application image supplied or created for your examination.

Also, the application must use the corresponding database configuration. Environment variable names must match what the application actually reads.

### **Explanation of every important field**

| Field               | Meaning                            |
| ------------------- | ---------------------------------- |
| services            | Defines the containers             |
| web                 | Web application service            |
| mysql               | Database service                   |
| image               | Docker image to download           |
| container_name      | Name of the container              |
| ports               | Maps host port to container port   |
| depends_on          | Defines service startup dependency |
| environment         | Sets environment variables         |
| MYSQL_ROOT_PASSWORD | Root password                      |
| MYSQL_DATABASE      | Database name                      |
| MYSQL_USER          | Database username                  |
| MYSQL_PASSWORD      | Database password                  |
| volumes             | Stores persistent database data    |

### **Understand port mapping**

```
ports:
  - "8080:8080"
```

Format:

`HOST_PORT:CONTAINER_PORT`

The first port belongs to the host machine. The second port belongs to the container.

For MySQL:

```
ports:
  - "3307:3306"
```

This means:

- Host machine port: 3307.
- MySQL container port: 3306.

Other containers should connect to MySQL using `mysql:3306`, not `localhost:3307`.

**1. A developer wants to temporarily stop all running services without removing containers, networks or configuration. Which command should be used?**

Answer:

Explanation: It stops all running services but preserves their containers and network configuration.

**2. After stopping services using docker compose stop, the developer wants to start the same containers again without recreating them. Which command should be executed?**

Answer:

```
docker compose start
```

Explanation: It starts previously stopped containers without creating new containers.

**3. Testing is complete, and the developer wants to stop and remove containers and the default network created by Compose. Which command should be used?**

Answer:

```
docker compose down
```

Explanation: It stops and removes containers and the Compose-created default network. Named volumes are retained unless `-v` is specified.

```
docker compose up -d
```

Answer:

```
docker compose stop backend
```

Explanation: Only the backend service is stopped. Frontend and database continue running.

## **5. Create Jenkinsfile**

A Jenkinsfile is a text file that defines the stages and steps of the Jenkins pipeline.

Create a file named:

`Jenkinsfile`

Use the following Groovy Scripted Pipeline:

```

node {

    try {

        stage('Checkout') {

            git branch: 'main',
                url: 'https://github.com/archanareddyse/OLTRS.git'

        }

        stage('Build and Test') {

            sh 'mvn clean verify'

        }

        stage('Docker Build') {

            sh '''
                docker build -t oltrs-app:latest .
            '''

        }

        stage('Docker Push') {

            withCredentials([
                usernamePassword(
                    credentialsId: 'dockerhub-creds',
                    usernameVariable: 'DOCKER_USER',
                    passwordVariable: 'DOCKER_PASS'
                )
            ]) {

                sh '''
                    echo "$DOCKER_PASS" | docker login \
                    -u "$DOCKER_USER" --password-stdin

                    docker tag oltrs-app:latest \
                    "$DOCKER_USER/oltrs-app:latest"

                    docker push "$DOCKER_USER/oltrs-app:latest"

                    docker logout
                '''

            }

        }

    }

    catch (err) {

        currentBuild.result = 'FAILURE'

        echo "Pipeline failed: ${err}"

        mail(
            to: 'student@example.com',
            subject: 'OLTRS Pipeline Failed',
            body: "The Jenkins pipeline failed. Check the console output."
        )

        throw err

    }

}

```

**Important adjustments before execution:**

- Change `main` to the actual default branch if it is named differently.
- The repository must contain a valid Dockerfile at its root for this example.
- The Dockerfile must match the actual project packaging (JAR or WAR) and runtime.
- Configure Maven and Docker on the Jenkins agent.
- Replace `student@example.com` with the intended notification address.
- The pipeline uses the Jenkins `sh` step and therefore assumes a Linux-based Jenkins agent. For Windows agents, use `bat` commands or an appropriate shell.

### **Explanation of each stage**

**Stage 1 – Checkout**

```
stage('Checkout') {
    git branch: 'main',
        url: 'https://github.com/archanareddyse/OLTRS.git'
}
```

Downloads the source code from GitHub into the Jenkins workspace.

**Stage 2 – Build and Test**

```
stage('Build and Test') {
    sh 'mvn clean verify'
}
```

- `clean` removes previous build files.
- `verify` compiles, tests and verifies the project.

If the build or tests fail, the pipeline throws an error and the subsequent Docker stages do not execute.

**Stage 3 – Docker Build**

```
docker build -t oltrs-app:latest .
```

Creates a Docker image from the Dockerfile.

**Stage 4 – Docker Push**

Jenkins retrieves Docker Hub credentials securely from its Credentials store.

Then:

```
docker login
docker tag

```

The final image will have this format:

```

```

**2. The Maven build fails during the Build stage. How will you ensure Docker Build and Push stages are skipped?**

Answer:

Use exception handling in the Scripted Pipeline.

```
try {

    stage('Build') {
        sh 'mvn clean verify'
    }

    stage('Docker Build') {
        sh 'docker build -t oltrs-app .'
    }

    stage('Docker Push') {
        sh 'docker push username/oltrs-app'
    }

}
catch (err) {

    echo "Build failed"

    throw err

}
```

When Maven fails, it throws an exception. Control moves to the catch block, so Docker Build and Docker Push are not executed.

**3. The pipeline successfully builds the application, but Docker Hub push fails due to authentication. How should credentials be configured and used securely?**

Answer:

1. Open Jenkins Credentials.
2. Add Docker Hub username and access token.
3. Give the credentials ID `dockerhub-creds`.
4. Retrieve them using `withCredentials`.
5. Use `docker login --password-stdin`.
6. Push the image after successful authentication.

Example:

```
withCredentials([
    usernamePassword(
        credentialsId: 'dockerhub-creds',
        usernameVariable: 'USER',
        passwordVariable: 'PASS'
    )
]) {
    sh '''
        echo "$PASS" | docker login \
        -u "$USER" --password-stdin
        docker push "$USER/oltrs-app:latest"
    '''
}
```

This prevents hardcoding credentials in the Jenkinsfile.

2. Select the pipeline job.
3. Open the failed build.
4. Check the Stage View or Pipeline Stage View.
5. Identify the stage marked as failed.
6. Open Console Output.
7. Read the error messages and correct the issue.

**5. The project team wants an email only when the pipeline fails. How would you implement this condition in the Scripted Pipeline?**

Answer:

Use a catch block and send an email only when an exception occurs.

```
try {

    stage('Build') {
        sh 'mvn clean verify'
    }

}
catch (err) {

    currentBuild.result = 'FAILURE'

    mail(
        to: 'student@example.com',
        subject: 'Build Failed',
```

## **7. Create Kubernetes Service**

A Service provides a stable network endpoint to access Pods.

We use NodePort to expose the application outside the cluster.

Create a file:

`service.yaml`

```

apiVersion: v1

metadata:
  name: oltrs-service

spec:
  type: NodePort

  selector:
    app: oltrs

  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080
      protocol: TCP

```

### **Explanation**

| Field      | Purpose                    |
| ---------- | -------------------------- |
| kind       | Service                    |
| name       | Service name               |
| type       | NodePort                   |
| selector   | Identifies matching Pods   |
| port       | Service port               |
| targetPort | Application container port |
| nodePort   | External node port         |
| protocol   | TCP communication          |

Remember:

- `port: 80` – Service port.
- `targetPort: 8080` – Port on which the application listens inside the container.
- `nodePort: 30080` – Port used to access the application through the Minikube node.

**Important:** The labels in the Deployment and selector in the Service must match. Here both use `app: oltrs`.

**1. A developer cannot connect to an EC2 instance using SSH. Which instance settings, key-pair permissions and Security Group rules should be checked?**

Answer:

Check the following:

2. Verify that the instance has a reachable public IP or DNS if connecting over the internet.
3. Verify that the correct private key pair is used.
4. Check that the `.pem` file has appropriate permissions.
5. Check that the SSH username is correct (`ubuntu` for Ubuntu AMIs, for example).

7. Verify that network ACLs, routing and internet gateway configuration allow SSH traffic.

**2. The web application runs successfully on the EC2 instance at port 8080, but users cannot access it through the public IP address. What configurations should be verified?**

Answer:

Check:

1. The application is running.
2. The application listens on port 8080.
3. The Security Group allows inbound TCP port 8080.
4. The instance has a public IPv4 address.
5. The subnet route table has a route to an Internet Gateway.
6. Network ACLs and the operating system firewall are not blocking the traffic.

Verify locally:

```
curl http://localhost:8080
```

If local access works but external access fails, investigate network and firewall configuration.

**3. An EC2 instance has no Public IPv4 address, but the application must be accessed over the internet. What AWS networking or addressing configuration is required?**

Answer:

The following options can be used:

- Assign an Elastic IP address to the EC2 instance.
- Place the instance in a public subnet with a route to an Internet Gateway.
- Configure suitable Security Group inbound rules.
- Alternatively, use a public Application Load Balancer to forward traffic to the instance.

An Elastic IP is a static public IPv4 address that can be associated with an EC2 instance.

**4. The application data must remain available after the EC2 instance is stopped and started. Which storage option and configuration should the developer consider?**

Answer:

Use Amazon EBS (Elastic Block Store).

EBS provides persistent block storage that can remain attached to an EC2 instance across stop and start operations.

Steps:

1. Create or select an EBS volume.
2. Attach it to the EC2 instance.
3. Format and mount the volume if necessary.
4. Store important application data on that volume.
5. Enable Delete on Termination = No if the volume must be retained when the instance is terminated.

Note: Instance-store storage is temporary and should not be used for data that must persist.

**5. An organization wants the application accessible through HTTP while restricting SSH access to administrators only. How should the Security Group inbound rules be configured?**

Answer:

Configure the following inbound rules:

| Type | Port | Source                         |
| ---- | ---- | ------------------------------ |
| HTTP | 80   | 0.0.0.0/0                      |
| SSH  | 22   | Administrator's public IP/CIDR |

Explanation:

- HTTP port 80 is accessible to everyone.
- SSH port 22 is restricted to authorized administrators.
- Do not configure SSH as `0.0.0.0/0`.

This improves the security of the EC2 instance.

| Comparison                 | Difference                                                                                          |
| -------------------------- | --------------------------------------------------------------------------------------------------- |
| Docker vs Docker Compose   | Docker manages containers; Compose manages multiple services using YAML.                            |

| Pod vs Deployment          | Pod runs containers; Deployment manages Pods and replicas.                                          |
| NodePort vs ClusterIP      | NodePort exposes a service through a node port; ClusterIP exposes it internally within the cluster. |

| EC2 vs EBS                 | EC2 provides computing; EBS provides persistent block storage.                                      |
| AMI vs Instance            | AMI is the machine image; instance is the virtual machine launched from it.                         |
| Security Group vs Key Pair | Security Group controls network access; Key Pair enables secure authentication.                     |

## **3. Create Deployment File**

**Go to VS Code → Create a file named&#x20;**`deployment.yaml`**.**

```
# Kubernetes API version
apiVersion: apps/v1

# Resource type
kind: Deployment

# Deployment details
metadata:
  name: oltrs-deployment

# Deployment specification
spec:

  # Initially create two replicas
  replicas: 2

  # Identify Pods using labels
  selector:
    matchLabels:
      app: oltrs

  # Pod configuration
  template:
    metadata:
      labels:
        app: oltrs

    spec:
      containers:

        # Application container
        - name: oltrs-container

          # Docker Hub image
          image: your-dockerhub-username/oltrs-app:latest

          # Application container port
          ports:
            - containerPort: 8080
```

## **4. Apply Deployment**

```
# Create Deployment
kubectl apply -f deployment.yaml

# Verify Deployment
kubectl get deployments

# Verify Pods
kubectl get pods

# Display detailed Deployment information
kubectl describe deployment oltrs-deployment
```

## **5. Create Service File**

**Go to VS Code → Create a file named&#x20;**`service.yaml`**.**

```
# Kubernetes API version
apiVersion: v1

# Resource type
kind: Service

# Service details
metadata:
  name: oltrs-service

# Service specification
spec:

  # Expose application using NodePort
  type: NodePort

  # Select Pods having this label
  selector:
    app: oltrs

  # Port configuration
  ports:

    # Service port
    - port: 80

      # Application container port
      targetPort: 8080

      # External NodePort
      nodePort: 30080

      # Network protocol
      protocol: TCP
```

## **6. Apply Service**

```

kubectl apply -f service.yaml

# Verify Services
kubectl get services

# Display detailed Service information
kubectl describe service oltrs-service
```
