# Kubernetes \& Minikube Practical Experiments

Practical command notes for the Kubernetes and Minikube work completed
on Windows using PowerShell and Docker Desktop.

> Run PowerShell with Docker Desktop open and running. These commands
> assume `kubectl` and `minikube` are installed. If a command reports
> that a resource already exists, inspect it with `kubectl get ...`
> before creating it again.

## Environment used

* Operating system: Windows
* Terminal: PowerShell
* Container driver: Docker Desktop (`--driver=docker`)
* Kubernetes cluster: Minikube
* `kubectl` client was installed and available.
* Minikube cluster was started successfully and kubectl was configured
to use the `minikube` context.

# Experiment 1 --- Check tools and start Minikube

# Experiment 7 --- Create a Deployment using YAML

## 1\. Create a working folder

``` powershell
mkdir C:\\Users\\LENOVO\\kubernetes-lab
cd C:\\Users\\LENOVO\\kubernetes-lab
```

## 2\. Create `deployment.yaml`

Create a file named `deployment.yaml` and paste this exact content:

``` yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
```

Save the file as `deployment.yaml` (not `deployment.yaml.txt`).

## 3\. Apply the YAML file

``` powershell
kubectl apply -f deployment.yaml
```

## 4\. Verify the Deployment

``` powershell
kubectl get deployments
kubectl get pods
kubectl get deployment nginx-deployment -o yaml
```

Part 1 — Docker Compose

1\. Temporarily stop all services without removing containers or networks

Answer: Use `docker compose stop`. It stops the running containers but keeps the containers, networks, volumes and

Compose configuration. This is useful when you want to pause the application and resume it later.

`docker compose stop`

Exam note: Do not use `docker compose down` for this requirement because `down` removes the containers and the

default network.

2\. Start the same stopped containers again

Answer: Use `docker compose start`. It starts existing stopped containers; it does not rebuild images or recreate

containers. You can start every service or name one service.

`docker compose start\\n# One service only\\ndocker compose start backend`

Exam note: Use `start` after `stop`. `up` is used when Compose may need to create or recreate resources.

3\. Stop and remove containers and the default network

Answer: Use `docker compose down`. Compose stops and removes the project's containers and the default network.

Named volumes are retained unless you explicitly request their removal.

`docker compose down`

Exam note: Add `-v` only if you intentionally want to remove the named and anonymous volumes associated with the

Compose project.

4\. Apply a newly added service in docker-compose.yml

Answer: Use `docker compose up -d`. Compose reads the updated file, creates the newly defined service and any

required resources, and starts the application in the background. It also reconciles other changed services where

needed.

`docker compose up -d\\n# Optionally target just the new service\\ndocker compose up -d new-service`

Exam note: If the service image must be rebuilt from a local Dockerfile, use `docker compose up -d --build`.

5\. Stop only the backend service

Answer: Specify the service name after the command. Compose stops only that service; the frontend and database

remain running. Be aware that dependent-service behavior can matter if dependency options are used.

`docker compose stop backend`

Exam note: Use the service key from the Compose YAML, not necessarily the container name.

6\. Launch the application again after docker compose down

Answer: Use `docker compose up -d`. Since `down` removed the containers and default network, Compose recreates

the required containers and network from the existing Compose configuration, then starts the services.

`docker compose up -d`

Exam note: If images need rebuilding from updated source, use `docker compose up -d --build`.

7\. Restart only the database after all services were stopped

Answer: Use `docker compose start db` (replace `db` with the actual database service key). This starts the existing

database container without starting the other stopped services.

`docker compose start database`

Exam note: If the database container was removed rather than merely stopped, `start` cannot bring it back; use

`docker compose up -d database` to create/start it.

8\. Rebuild images, recreate containers if required, and start all services

Answer: Use `docker compose up -d --build`. The `--build` option builds images before starting. Compose recreates

containers when it detects that the service configuration or image has changed, while keeping persistent named

volumes unless removed separately.

`docker compose up -d --build`

Exam note: For a clean forced recreation, `docker compose up -d --build --force-recreate` can be used, but it causes

avoidable downtime.

9\. Remove containers and networks but preserve named-volume database data

Answer: Run `docker compose down` without the volume-removal option. This removes containers and the default

network but leaves named volumes intact, so database data can be reused when the project is brought up again.

`docker compose down`

Exam note: Avoid `docker compose down -v` (or `--volumes`), because it removes named volumes declared by the

Compose project and can permanently delete database data.

Part 2 — Jenkins CI/CD

10\. Jenkins does not start after a new GitHub commit

Answer: Check the integration from source control to Jenkins: (1) the job's repository URL and branch are correct; (2)

GitHub webhook points to the correct Jenkins URL and `/github-webhook/`; (3) the webhook is enabled and its recent

deliveries return a successful response; (4) Jenkins has the GitHub integration/webhook trigger enabled (or the correct

Multibranch Pipeline scan trigger); (5) Jenkins is reachable from GitHub; (6) credentials have repository access; and

(7) branch filters or path filters are not excluding the commit. Check Jenkins system/job logs and GitHub webhook

delivery details.

`# Typical webhook endpoint\\nhttps://<jenkins-host>/github-webhook/`

Exam note: For a Multibranch Pipeline, also verify branch indexing and the presence/location of the Jenkinsfile in the

pushed branch.

11\. Skip Docker Build and Push when Maven Build fails

Answer: Make the Docker stages conditional on a successful build. In a Declarative Pipeline, later stages are normally

skipped after an earlier stage fails unless the pipeline explicitly catches/handles the failure. In Scripted Pipeline, allow

the Maven exception to propagate or set a success flag and test it before Docker operations.

`stage('Build') {\\n    sh 'mvn clean package'\\n}\\nstage('Docker Build') {\\n    sh 'docker build -t myapp:latest .'\\n}\\nstage('Docker Push') {\\n    sh 'docker push myapp:latest'\\n}`

Exam note: Do not wrap the Maven command in `catchError` or a broad `try/catch` that swallows the failure unless

you also explicitly prevent subsequent Docker stages from running.

12\. Configure Docker Hub credentials securely in Jenkinsfile

Answer: Create a Jenkins credential (typically Username with password, or a Docker Hub access token) in Manage

Jenkins fi Credentials. Give it a credential ID, then bind it at runtime using `withCredentials` or the Docker Pipeline

`docker.withRegistry` helper. Never hard-code usernames, passwords or tokens in the Jenkinsfile, repository, build

arguments or console output. Prefer a least-privilege access token and rotate it when required.

Exam note: Use single-quoted Groovy strings around shell commands so Groovy does not interpolate the secret.

Jenkins masks bound credentials in logs, but avoid printing them or enabling shell tracing (`set -x`).

13\. Find which deployment stage failed and inspect the error

Answer: Open the Jenkins job fi select the failed build number fi open Console Output. The Stage View or Pipeline

Steps view identifies the stage that failed; select the stage/step to inspect its logs. Look for the first meaningful error,

exit code, failed command, credentials/permission issue, unavailable host, or deployment timeout. Also inspect agent

logs and the target server/cluster logs where relevant.

`# Useful pipeline diagnostic commands\\necho "Deploying build ${BUILD\_NUMBER}"\\nwhoami\\nhostname\\n`

Exam note: Re-run only after identifying the root cause. If the pipeline uses `post { always { ... } }`, publish logs or test

reports there so they remain available after failure.

14\. Send email only when a Scripted Pipeline fails

Answer: Use a `try/catch/finally` pattern. Send the failure email in `catch`, then rethrow the exception so Jenkins still

marks the build as failed. Successful execution passes through without sending an email. Configure the Jenkins mail

provider/SMTP settings and use the Email Extension plugin if using `emailext`.

`try {\\n    node {\\n        stage('Checkout') { checkout scm }\\n        stage('Build') { sh 'mvn clean package' }\\n        stage('Deploy') { sh './deploy.sh' }\\n    }\\n} catch (err) {\\n    emailext(to: 'team@example.com',\\n        subject: "FAILED: ${env.JOB\_NAME} #${env.BUILD\_NUMBER}",\\n        body: "Build failed. See ${env.BUILD\_URL} for details.")\\n    throw err\\n}`

Exam note: Replace the example recipient with the real team address. If email itself fails, ensure that notification

failure does not hide the original build failure.

Part 3 — Kubernetes

15\. Run four application instances in a Kubernetes cluster

Answer: Create a Deployment that references the built image and specifies `replicas: 4`. A Deployment manages a

ReplicaSet, which maintains the desired number of Pods and replaces failed/deleted Pods. Apply the manifest and

verify the rollout.

`apiVersion: apps/v1\\nkind: Deployment\\nmetadata:\\n  name: web-app\\nspec:\\n  replicas: 4\\n  selector:\\n    matchLabels:\\n      app: web-app\\n  template:\\n    metadata:\\n      labels:\\n        app: web-app\\n    spec:\\n      containers:\\n      - name: web-app\\n        image: yourname/web-app:1.0\\n        ports:\\n        - containerPort: 8080\\n\\n# Apply and verify\\nkubectl apply -f deployment.yaml\\nkubectl get deployments,pods`

Exam note: Use a Deployment rather than creating four standalone Pods, because it provides declarative replica

management and self-healing.

16\. Expose a running Pod to users outside the cluster

Answer: Create a Kubernetes Service. For a simple lab/cluster, use `NodePort` to expose a port on each worker

node; in a cloud environment, use `LoadBalancer` where supported. For HTTP routing to multiple services/domains,

configure an Ingress controller and an Ingress resource.

`kubectl expose deployment web-app --type=NodePort --port=80 --target-port=8080\\nkubectl get service web-app`

Exam note: A Pod's IP is generally internal and ephemeral. A Service provides a stable virtual IP/DNS name and

routes traffic to matching ready Pods.

17\. Only two of four replicas are Running

Answer: Inspect the Deployment, ReplicaSet and all Pods. Use `kubectl get pods -o wide`, then `kubectl describe pod

` for Events and status details. Check container logs with `kubectl logs ` (and `-c ` for multi-container Pods). Common

causes include image pull errors, insufficient CPU/memory, failed scheduling, crash loops, failed probes, invalid

configuration/secrets, or storage mount problems.

`kubectl get deployment,rs,pods\\nkubectl describe deployment web-app\\nkubectl describe pod <pod-name>\\nkubectl logs <pod-name> --previous\\nkubectl get events --sort-by=.metadata.creationTimestamp`

Exam note: Use the Events section to distinguish scheduling/image-pull problems from application crashes. Fix the

underlying cause and verify all four replicas become Ready.

18\. Ensure the application is recreated after a worker node fails

Answer: Run the application under a Deployment (or StatefulSet for stateful workloads), not as a manually created

standalone Pod. The Kubernetes control plane detects unavailable Pods/nodes and the controllers work to maintain

the desired replica count on healthy nodes, subject to cluster capacity and scheduling constraints.

`kubectl create deployment web-app --image=yourname/web-app:1.0 --replicas=3\\nkubectl get deployments,pods -o wide`

Exam note: A Deployment recreates stateless Pods; persistent data requires appropriate persistent volumes and

storage configuration. Node failure recovery also depends on a functioning control plane and available worker

capacity.

19\. Scale a Deployment from three to six replicas

Answer: Use `kubectl scale` to change the desired replica count without deleting and recreating the Deployment.

Kubernetes creates additional Pods and the Deployment controller maintains six replicas.

`kubectl scale deployment web-app --replicas=6\\nkubectl get deployment web-app\\nkubectl get pods -l app=web-app`

Exam note: To make the change permanent in source-controlled configuration, also update `spec.replicas` in the

Deployment YAML and apply it; otherwise a later apply may reset the count.

20\. NodePort works on one worker node but not another

Answer: Check that the Service is truly NodePort and note its assigned nodePort. Verify the second node is Ready

and reachable, and that routing/firewall/security rules allow that TCP port. Check kube-proxy (or the cluster's

replacement dataplane), CNI/network routing, host firewall rules, cloud security groups, and whether the node is in a

healthy state. Confirm the Service has ready endpoints.

`kubectl get svc <service-name> -o wide\\nkubectl describe svc <service-name>\\nkubectl get endpoints <service-name>\\nkubectl get nodes -o wide`

Exam note: Test the same `http://:` from a machine that can reach each node. A NodePort is normally exposed on

eligible nodes, but network/firewall and cluster configuration can prevent access.

21\. Kubernetes continues running the old Docker image

Answer: Build and push the updated image, preferably with a new immutable tag (for example, `1.1` or a commit

SHA), then update the Deployment's image. Monitor the rollout. Avoid relying on a reused `latest` tag because nodes

may retain cached images and the deployment may not detect a changed image reference.

`docker build -t yourname/web-app:1.1 .\\ndocker push yourname/web-app:1.1\\nkubectl set image deployment/web-app web-app=yourname/web-app:1.1\\nkubectl rollout status deployment/web-app`

Exam note: If you must reuse a tag, set `imagePullPolicy: Always` and trigger a rollout, but unique version tags are

more reliable and auditable.

22\. Frontend communicates with backend despite changing Pod IPs

Answer: Expose the backend Pods through a Kubernetes Service with a stable name and port. The frontend calls the

backend using the Service DNS name, such as `http://backend:8080` when both are in the same namespace.

Kubernetes updates Service endpoints as backend Pods are replaced.

`apiVersion: v1\\nkind: Service\\nmetadata:\\n  name: backend\\nspec:\\n  selector:\\n    app: backend\\n  ports:\\n  - port: 8080\\n    targetPort: 8080`

Exam note: For a different namespace, use a fully qualified DNS name such as `backend.team-a.svc.cluster.local`.

Ensure the Service selector matches the backend Pod labels.

23\. Deployment has four desired replicas but Service has no endpoints

Answer: Check whether Pods are Ready and whether the Service selector matches their labels exactly. Inspect the

Service and EndpointSlices, Pod readiness conditions, port/targetPort values and readiness probes. A Service only

routes to eligible endpoints; unready Pods are normally excluded.

`kubectl get pods --show-labels\\nkubectl describe svc <service-name>\\nkubectl get endpoints <service-name>\\nkubectl get endpointslices\\nkubectl describe pod <pod-name>`

Exam note: Correct the selector/labels mismatch, wrong target port, failed readiness probe or application listener

issue. Confirm endpoints appear and test the Service from inside the cluster.

24\. Remove application resources without deleting the cluster

Answer: Delete the resources created for the application using their manifest, or delete the named Deployment and

Service. Deleting a Deployment also removes its ReplicaSet and managed Pods. This does not delete the Kubernetes

cluster itself.

`kubectl delete -f deployment.yaml\\nkubectl delete -f service.yaml\\n# Or by resource name\\nkubectl delete deployment web-app\\nkubectl delete service web-app\\nkubectl get all`

Exam note: Check for related ConfigMaps, Secrets, Ingresses and PVCs if they were created. Delete persistent

volume claims only when you intentionally want to remove the associated data.

Part 4 — AWS EC2

25\. Deploy a Java web application on an AWS EC2 instance

Answer: Launch an EC2 instance using a suitable Linux AMI and instance type. Configure a key pair and a Security

Group that allows SSH (TCP 22) only from an administrator IP and HTTP/HTTPS (80/443) from intended users.

Connect using SSH, install a supported Java runtime and web server/container runtime if required, copy or clone the

application, configure environment variables and database connectivity, then run the packaged JAR or deploy the

WAR to a servlet container such as Tomcat. Verify locally, then test via the public DNS/IP. For production, use HTTPS,

a domain, monitoring, backups and least-privilege IAM.

`ssh -i key.pem ec2-user@<public-ip>\\nsudo dnf update -y\\nsudo dnf install java-17-amazon-corretto -y\\njava -jar app.jar`

Exam note: AMI username varies (for example, `ec2-user` on Amazon Linux and `ubuntu` on Ubuntu). Keep secrets

out of source code and use an appropriate secret store or protected configuration.

26\. Cannot connect to EC2 using SSH

Answer: Check: (1) instance state is Running and status checks pass; (2) correct public IPv4/DNS or reachable

private route is used; (3) Security Group inbound rule permits TCP 22 from your current public IP; (4) subnet route

table has a route to an Internet Gateway for public access; (5) network ACL allows inbound SSH and return traffic; (6)

correct private key and OS username are used; (7) local firewall/VPN/network is not blocking SSH; and (8) the

instance OS firewall/sshd is running. For private instances, use a bastion host, VPN or Systems Manager Session

Manager.

`ssh -vvv -i key.pem ec2-user@<public-ip>\\n# Check instance status checks and Security Group rules in the EC2 console`

Exam note: Do not open SSH to `0.0.0.0/0` as a routine fix. Restrict it to trusted administrator IP ranges.

27\. Application listens on port 8080 but is not reachable publicly

Answer: Check that the application is listening on `0.0.0.0:8080` rather than only `127.0.0.1`, and that it is actually

running. The EC2 Security Group must allow inbound TCP 8080 from the intended source. Also inspect subnet

routing, Internet Gateway, network ACLs, OS firewall (firewalld/ufw/iptables), container port publishing and the

application's own logs.

`sudo ss -lntp | grep 8080\\ncurl -v http://localhost:8080\\nsudo firewall-cmd --list-ports\\n# If using Docker, check: docker ps`

Exam note: If users should access a standard website, a reverse proxy or load balancer can expose 80/443 and

forward traffic internally to 8080.

28\. EC2 instance has no public IP address

Answer: Preferred options: associate an Elastic IP with the instance's network interface, or launch/replace the

29\. Configure Nagios to monitor whether a hosted web application responds

Answer: Use the Nagios HTTP plugin (`check\_http`) to request the application URL and validate the expected

response. Define a command and a service check for the host. Set warning/critical thresholds for response time or

expected content where appropriate, then reload/restart Nagios and verify the service status.

`define command {\\n  command\_name check\_web\_app\\n  command\_line $USER1$/check\_http -H $HOSTADDRESS$ -p 8080 -u / -s 'Welcome' -w 3 -c 5\\n}\\n\\ndefine service {\\n  use                 generic-service\\n  host\_name           app-server\\n  service\_description Web Application\\n  check\_command       check\_web\_app\\n}`

Exam note: Ensure the plugin exists and is executable, the Nagios server can reach the target port, and the expected

string is genuinely present. Adjust path, port and response text to the application.

30\. Monitor increasing CPU usage and generate Nagios alerts

Answer: Install/configure the Nagios Remote Plugin Executor (NRPE) on the Linux server, or use an approved

agent/monitoring method. Configure a remote command that runs a CPU/load plugin such as `check\_load`, define the

corresponding command and service on the Nagios server, and set warning/critical thresholds. Nagios periodically

runs the check and changes state when thresholds are crossed.

`# Example command on monitored host (NRPE)\\ncommand\[check\_load]=/usr/lib/nagios/plugins/check\_load -w 5,4,3 -c 10,8,6\\n\\n# On Nagios server: service check\\ndefine service {\\n  use                 generic-service\\n  host\_name           app-server\\n  service\_description CPU Load\\n  check\_command       check\_nrpe!check\_load\\n}`

Exam note: `check\_load` measures system load averages, not a direct CPU percentage. For CPU percentage, use a

suitable plugin (for example, one based on `mpstat`) and configure thresholds that match the server's CPU count and

workload.

31\. Notify before a disk partition becomes full

Answer: Use a disk monitoring plugin such as `check\_disk` on the monitored host (often through NRPE). Configure

warning and critical thresholds by free space or percentage used, define a Nagios service check, and enable

notifications for warning/critical states. Set thresholds with enough headroom for the administrator to respond.

`# Example: warn below 20% free, critical below 10% free\\ncommand\[check\_disk]=/usr/lib/nagios/plugins/check\_disk -w 20% -c 10% -p /\\n\\n# Nagios service\\ndefine service {\\n  use                 generic-service\\n  host\_name           app-server\\n  service\_description Root Disk\\n  check\_command       check\_nrpe!check\_disk\\n}`

Exam note: Confirm the plugin's threshold semantics and filesystem mount point. Monitor important data partitions

separately where appropriate.

32\. Nagios reports UNKNOWN for a Linux server

Answer: UNKNOWN usually means the check could not determine a valid state, rather than confirming the

host/service is healthy or failed. Inspect the service details and plugin output. Common causes include missing

plugin/command, incorrect command arguments, plugin timeout, permission problems, malformed output/exit code,

NRPE not running, blocked NRPE port (commonly TCP 5666), hostname/allowed-host mismatch, or incompatible

plugin paths. Run the exact plugin command manually on the relevant machine and inspect Nagios/NRPE logs.

`/usr/lib/nagios/plugins/check\_disk -w 20% -c 10% -p /\\nsystemctl status nagios-nrpe-server\\nsudo journalctl -u nagios-nrpe-server --since '30 minutes ago'`

Exam note: Fix the command, permissions, connectivity or agent configuration, then re-run the check. Use the actual

plugin path and service name for the installed distribution.

33\. Monitor five Linux servers from one central Nagios server

Answer: Install Nagios Core and its plugins on a central monitoring server. Give each Linux server a unique

hostname/address and configure host objects on the Nagios server. Install NRPE and required plugins on each

monitored server, allow the Nagios server's IP in NRPE configuration and firewall rules, and define remote checks for

CPU, disk, memory/load and application services. Validate the configuration before restarting/reloading Nagios.

`# On each monitored Linux host: allow the monitoring server\\nallowed\_hosts=127.0.0.1,<NAGIOS\_SERVER\_IP>\\n\\n# On Nagios server, validate and restart (paths vary)\\nnagios -v /usr/local/nagios/etc/nagios.cfg\\nsudo systemctl restart nagios`

Exam note: Organize host definitions into separate files or templates to simplify maintenance. Secure NRPE

communication and expose only required ports.

content, timeout and threshold values. Check plugin exit codes and output: 0=OK, 1=WARNING, 2=CRITICAL,

3=UNKNOWN. Test from the same network location as Nagios, because the service may work locally but fail remotely.

35\. Email when a host goes DOWN and again when it comes UP

Answer: Configure valid SMTP/mail delivery on the Nagios host, define a contact with an email address, and enable

host notifications for DOWN and recovery (UP) states. Attach the contact/contact group to the host, set notification

options and periods, and ensure global and host notification settings are enabled. Test mail delivery and notification

Exam note: `d` means DOWN, `u` means UNREACHABLE and `r` means recovery. If only DOWN and UP recovery

36\. Verify the EC2 Security Group allows required inbound traffic

Answer: Open EC2 fi Instances fi select the instance fi Security tab fi click its Security Group. Under Inbound

rules, confirm there is a rule for the protocol and port the application uses (for example, TCP 80 for HTTP, 443 for

HTTPS, or 8080 for a direct test) and that the source CIDR includes the intended client. Confirm the correct Security

Group is attached to the instance's network interface. Check outbound rules and NACLs if return traffic is blocked.

`# From a client machine\\ncurl -v http://<public-ip>:8080\\n# On the instance\\nsudo ss -lntp`

Exam note: Use the narrowest source range practical. For a public website, HTTP/HTTPS may be open to all; SSH

should normally be limited to administrator IPs.

37\. Upgrade EC2 instance configuration when traffic increases

Answer: First assess CPU, memory, network and application metrics (for example, CloudWatch and OS-level

monitoring). If the instance is undersized, choose a larger or more suitable instance type. Commonly: stop the

instance, change Instance type under EC2 fi Instance state/Instance settings, then start it. Verify architecture and AMI

compatibility, available quotas, storage/network needs and licensing. For minimal downtime and higher availability,

consider deploying a replacement behind a load balancer or using an Auto Scaling Group rather than resizing a single

server.

`# Typical AWS CLI sequence (review instance state/type first)\\naws ec2 stop-instances --instance-ids i-xxxxxxxx\\naws ec2 modify-instance-attribute --instance-id i-xxxxxxxx --instance-type '{"Value":"t3.large"}'\\naws ec2 start-instances --instance-ids i-xxxxxxxx`

Exam note: Stopping can affect ephemeral instance-store data and may change an auto-assigned public IPv4

address. An Elastic IP remains associated unless disassociated.

38\. Keep important files available after stopping and starting EC2

Answer: Store persistent files on an Amazon EBS volume rather than relying on instance-store storage or temporary

filesystems. EBS volumes persist independently of the running instance and can be mounted again after stop/start. For

durable shared or highly available file storage, consider EFS or S3 depending on access pattern. Back up important

data with EBS snapshots and test restoration.

`# Inspect attached block devices\\nlsblk\\n# Mount an existing formatted EBS filesystem (example only)\\nsudo mkdir -p /data\\nsudo mount /dev/nvme1n1 /data`

Exam note: Use the correct device identifier and filesystem; do not format an existing data volume. Configure

`/etc/fstab` carefully using UUIDs so the volume mounts after reboot.

39\. Recover application data after accidentally terminating EC2

Answer: Recovery depends on the storage configuration and the EBS DeleteOnTermination setting. The root EBS

volume is often configured for deletion on termination, while separately attached data volumes may be retained. Check

EC2 fi Volumes for available detached volumes and inspect snapshots/backups. If a volume remains, attach it to a

recovery instance, mount it read-only first where appropriate, and copy the data. If deleted, restore from an EBS

snapshot or backup. Rebuild the application on a new EC2 instance and reattach/restore the data.

`# On recovery instance, identify devices\\nlsblk\\nsudo mkdir -p /recovery\\nsudo mount -o ro /dev/nvme1n1p1 /recovery`

40\. Allow HTTP publicly but restrict SSH to administrators

Answer: Edit the EC2 Security Group inbound rules. Add HTTP TCP 80 from `0.0.0.0/0` (and `::/0` if IPv6 public

access is intended). Add SSH TCP 22 only from the administrator's fixed public IP in `/32` form or an approved

corporate VPN/bastion range. Remove any SSH rule that allows all sources. Keep only required outbound access and

review NACLs.

`Inbound rules example:\\nHTTP  TCP 80  Source: 0.0.0.0/0\\nSSH   TCP 22  Source: <ADMIN\_PUBLIC\_IP>/32`

Exam note: For production, redirect HTTP to HTTPS and expose TCP 443. Avoid unrestricted SSH; consider

Systems Manager Session Manager for access without opening port 22.

41\. Keep a consistent public IP when EC2 public IP changes

Answer: Allocate an Elastic IP address (EIP) in the same AWS Region and associate it with the instance or its

network interface. The EIP is a static public IPv4 address that remains stable across normal stop/start operations while

it stays allocated and associated. Update DNS records to point to the EIP if a domain is used.

`# AWS Console: EC2 fi Network \& Security fi Elastic IPs\\n# Allocate Elastic IP fi select it fi Actions fi Associate Elastic IP address`

Exam note: Elastic IPs can incur charges in some circumstances, including certain unassociated or otherwise

chargeable usage. For scalable production deployments, a load balancer with DNS may be more suitable than binding

users directly to one instance.

containers/network; up -d = create/start; up -d --build = build and start; down -v = also remove volumes (data-loss risk).
